# Архитектура сервиса распознавания вин «Своё Вино»

## Назначение и продуктовая идея

Пользователь фотографирует этикетку российского вина — и получает карточку из
каталога платформы «Своё Вино» (vino-svoe.ru): название, производитель, сорта,
регион, рейтинг, фото. Ключевое требование — **офлайн-first**: винотека, дача,
подвал магазина — сценарии без сети. Поэтому вся цепочка «фото → OCR → поиск →
карточка» исполняется на устройстве; сеть нужна один раз, при установке.

Продукт поставляется в трёх видах из одной кодовой базы данных и одного ядра:

- [app/](../app/) — устанавливаемая PWA (MVP, три таба: Скан / Каталог / Мои вина);
- [mobile/](../mobile/) — Flutter-приложение Android/iOS (прод-трек);
- [core/](../core/) — Python-референс ядра + eval-стенд.

## Ключевой принцип: закрытый справочник вместо «понимания»

База конечна: **2017 вин**. Задача не «прочитать и понять этикетку», а «найти
ближайшую запись в известном списке». Это радикально снижает требования к OCR:
достаточно, чтобы из зашумлённого текста выжило несколько информативных токенов
(бренд, линейка, сорт) — IDF-взвешенный fuzzy-матчер дотянет остальное.
Практическое следствие: латинский OCR (ML Kit) компенсируется жадной
транслитерацией лат→кир в канонизации, а опечатки движка — префиксным матчем и
Левенштейном. Confidence нормируется на «идеальный матч заголовка», что даёт
честную шкалу для UI-порогов (0.45 / 0.22).

## Компоненты и потоки данных

**Серверный (офлайновый по расписанию) контур — ETL.** [etl/scrape.py](../etl/scrape.py)
обходит sitemap и `GET /api/wines/{slug}` (0 ошибок на полной выгрузке), фото
берутся через resize-прокси `api.vino-svoe.ru/v1/img/.../400/...` (~10 KB/шт.,
18 MB всего). [etl/build_datapack.py](../etl/build_datapack.py) собирает датапак:
`data/datapack/wines.json` (2.2 MB) и `wines.sqlite` с FTS5 (2.2 MB), в meta —
версия и hash. [etl/update.sh](../etl/update.sh) — resume-safe докачка новых вин
и пересборка; пригоден для крона.

**Клиенты.** Датапак и фото вшиваются в бандл (PWA ~32 MB, APK release 97 MB
universal, `--split-per-abi` ≈ на треть меньше на устройство). Пайплайн на
устройстве: камера/галерея → OCR → канонизация → матчер → карточка. История,
избранное, оценки — локально (localStorage / shared_preferences).

**Серверный fallback вне критического пути.** Контур с VLM (Qwen2.5-VL) для
спорных фото при наличии сети спроектирован, но не реализован; офлайн-путь от
него не зависит.

## Три зеркала ядра и дисциплина синхронизации

Ядро (канонизация + матчер) существует в трёх реализациях с идентичной логикой:

| Зеркало | Файлы | Роль |
|---|---|---|
| Python | [core/normalize.py](../core/normalize.py), [core/matcher.py](../core/matcher.py) | референс, прототипирование |
| JS | [app/js/normalize.js](../app/js/normalize.js), [app/js/matcher.js](../app/js/matcher.js) | PWA + eval + генерация golden |
| Dart | [mobile/lib/core/normalize.dart](../mobile/lib/core/normalize.dart), [mobile/lib/core/matcher.dart](../mobile/lib/core/matcher.dart) | Flutter |

Общая логика: жадный диграфный транслит LAT2CYR, только шумовые стоп-слова
(категорийные «брют»/«белое» участвуют в матчинге), веса полей title 3.0 /
manufacturer 2.0 / grapes 1.0 / region+category 0.5, IDF = 0.5+ln(n/df)/ln(n),
матч токена: точный 1.0 / префикс ≥4 при разнице длин ≤3 — 0.85 / Левенштейн ≤1 (len≥5) или ≤2 (len≥8)
0.7; confidence = score/(Σidf×3.0), бонус года +0.1 (cap 1.0), отсечка 0.02,
tie-break по rating desc. Известная ловушка: турецкая `İ` унифицируется
`replaceAll('İ','I')` до lowercase — во всех трёх зеркалах.

Синхронизация держится тестами, а не дисциплиной чтения диффов:
[tools/gen_golden.mjs](../tools/gen_golden.mjs) прогоняет 30 эталонных запросов
через JS-ядро и пишет [mobile/test/golden_parity.json](../mobile/test/golden_parity.json);
[mobile/test/parity_test.dart](../mobile/test/parity_test.dart) сверяет Dart с
golden с точностью 1e-4. **Правило: любая правка ядра = правка всех трёх зеркал
+ перегенерация golden + `flutter test`.**

## Выбор технологий и почему

**PWA первой** — скорость проверки гипотезы: без сторов, без сборки, итерация в
браузере. Tesseract.js rus+eng в бандле (vendor 12 MB) даёт настоящую кириллицу
офлайн; два OCR-прохода (полный кадр + кроп зоны этикетки, grayscale + contrast
1.3, таргет 1400px) подняли eval на неудобном кейсе: top-1 16→23.3%, top-5 30→38%. SW: precache
shell (16 записей), фото cache-on-demand, wines.json network-first — полный
офлайн после первой загрузки. Поиск по 2017 винам ~66 мс на JS — индексы не нужны.

**Flutter для прода** — у web-стека потолок: на iOS нет надёжного доступа к
нативному OCR, Tesseract.js медленный и тяжёлый. Прод-пути OCR: Apple Vision на
iOS (кириллица из коробки), Tesseract FFI на Android, серверный fallback. В MVP
mobile использует ML Kit (только latin script — кириллической модели у ML Kit
нет), что и оправдывает транслитерацию в ядре. Грабли сборки: R8 требует
proguard-правил (`-dontwarn` CJK-скрипты + `-keep com.google.mlkit.**`), иначе
падение сборки или NPE в рантайме.

**Качество сейчас** ([core/eval.mjs](../core/eval.mjs), тот же Tesseract-стек,
150 фото 1200px полной бутылки): top-1 23.3%, top-5 38.0%. Это худший кейс —
стекло, мелкая этикетка в кадре; прицельные фото этикетки дают conf 1.0 в живом
тесте. PSM11 выигрыша не дал.

## Ограничения и роадмап

- **Юридическое.** robots.txt vino-svoe.ru запрещает `/api/*`. Пилот работает со
  щадящим rate limit и честным UA; продакшн и регулярные обновления датапака
  требуют договорённости с платформой.
- **Полевой тестсет.** Текущий eval — синтетика по каталожным фото; нужны
  реальные снимки с телефонов (блики, наклон, полки) для честной метрики и
  подбора порогов UI.
- **MobileCLIP kNN.** Визуальный эмбеддинг этикетки + kNN по базе — второй
  канал распознавания, независимый от текста; закрытый справочник делает это
  задачей retrieval, а не классификации.
- **Серверный VLM-fallback.** Qwen2.5-VL для фото, где OCR-канал даёт низкий
  confidence и есть сеть; интерфейс — тот же матчер поверх извлечённых полей.
- **Прод-OCR в mobile.** Замена ML Kit latin на Apple Vision (iOS) и Tesseract
  FFI (Android) по прод-путям, паритет через тот же golden-механизм.
